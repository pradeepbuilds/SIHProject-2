# 07 — Technical Implementation

## 1. Feature table (conceptual)

| Column | Type | Category |
|---|---|---|
| `location_id` | string | METADATA |
| `panchayat_id` / `grid_cell_id` | string | METADATA |
| `block_id`, `district_id` | string | METADATA |
| `latitude`, `longitude` | float | METADATA |
| `forecast_date` | date | METADATA (when the coarse forecast was issued) |
| `target_date` | date | METADATA (the date the prediction is valid for) |
| `horizon_days` (= lead time, `target_date − forecast_date`) | int | **FEATURE, first-class** — not just metadata. Forecast error characteristics change materially with lead time (+1 day vs +5 days), so the model must see this value directly, not just have it implied by which row it's scoring. Carried through database records, API responses, model training/evaluation, and dashboard displays (kept as the same field name, `horizon_days`, used throughout `08_API_AND_DATABASE.md` and `11_AGENT_BUILD_PLAN.md`) |
| `timestamp` | datetime | METADATA (kept for backward-compatible ordering; `forecast_date`/`target_date`/`horizon_days` are authoritative) |
| `coarse_temperature_max`, `coarse_temperature_min` | float | FEATURE |
| `coarse_rainfall` | float | FEATURE |
| `coarse_humidity` | float | FEATURE |
| `coarse_wind_speed` | float | FEATURE |
| `elevation`, `slope`, `aspect` | float | FEATURE (derived from DEM) |
| `land_cover_class` | categorical | FEATURE (from LULC) |
| `ndvi`, `ndwi` | float | FEATURE (derived, Sentinel-2) |
| `soil_texture_class` | categorical | FEATURE |
| `distance_to_water_km` | float | FEATURE (derived, GIS) |
| `historical_temperature_mean`, `historical_rainfall_mean` | float | DERIVED FEATURE (climatology from historical obs/reanalysis) |
| `target_temperature_max`, `target_temperature_min` | float | LABEL (only present in training data, from ground obs) |
| `target_rainfall` | float | LABEL |
| `target_humidity` | float | LABEL |
| `p10`, `p50`, `p90` | float | derived OUTPUT (not input) — quantile interval, matches `PredictionUncertainty` in `08_API_AND_DATABASE.md` §2 |
| `uncertainty_label` | enum {`low`, `medium`, `high`} | derived OUTPUT — from interval width; `low` = narrow/most trustworthy, `high` = wide/least trustworthy (direction convention: `04_ML_DOWNSCALING_APPROACH.md` §3) |
| `data_source_tag` | enum {OBSERVED, FORECAST, BASELINE, ML_DOWNSCALED} | METADATA — see note below |
| `is_synthetic` | boolean | METADATA — independent of `data_source_tag` (see note below) |

**Provenance is two independent fields, never conflated into one.** `data_source_tag` answers
*"what kind of value is this"* (an observation, a passthrough coarse forecast, the Block
Replication/IDW baseline, or this system's ML output). `is_synthetic` answers a completely
separate question — *"was this value generated by the synthetic-data fallback generator, or is
it real"* — and applies equally to any of the four tags (a synthetic observation is still
`data_source_tag = OBSERVED, is_synthetic = true`; a real ML prediction, once real data is used,
is `data_source_tag = ML_DOWNSCALED, is_synthetic = false`). The **Block Replication Baseline and
any secondary IDW baseline are tagged `BASELINE`, never `ML_DOWNSCALED`** — a baseline is not a
model prediction, and mislabeling it as `ML_DOWNSCALED` would silently overstate what the ML
system actually did. If a value's provenance is genuinely unknown or ambiguous, it must **not**
be silently assigned any tag — it is flagged as invalid/unknown and the ambiguity is resolved
explicitly (by a human or an upstream fix), never guessed.

Pressure is **excluded** per the reasoning in `01_PROBLEM_ANALYSIS.md` §H. Population/built-up
indicators are **deferred**: they may help an urban-heat-style correction but were not verified
against a specific open dataset for the pilot district and are not included until one is
confirmed (avoiding fabrication per Rule 1).

### Required vs. optional MVP features

To keep the MVP from being blocked by any one dataset's availability, the feature set above
splits into two tiers:

- **Required for the MVP** (the core experiment must work with only these): `latitude`,
  `longitude`, `elevation`, plus the relevant `coarse_*` block-forecast value(s) and
  `horizon_days`.
- **Optional/enhanced** (added when available, but their absence must never block a build):
  `slope`, `aspect`, `land_cover_class`, `ndvi`/`ndwi`, `soil_texture_class`,
  `distance_to_water_km`, `historical_*_mean`. If external raster data for any of these is
  unavailable for the pilot district, the coding agent proceeds with the required tier alone
  rather than stalling the project on a missing layer.

## 2. Spatial representation

| Option | Tradeoff |
|---|---|
| Panchayat polygons | Matches the PS's own terminology exactly; but boundary availability is fragmented (see `03`, §7.5) |
| Regular high-resolution grid (e.g. 1 km) | Always constructible from a block boundary regardless of panchayat-polygon availability; easy to aggregate up to panchayat by spatial join once boundaries exist | 
| Farm/plot polygons | Not available at national scale; explicit future extension only |
| Lat/long points (station-like) | Simplest for point validation against AWS stations, but doesn't directly answer "what's the panchayat-level forecast" |
| Raster pixels | Natural for CNN/U-Net approaches (Section 04) — not the chosen ML family for MVP |

**Decision for the prototype:** use a **1 km regular grid clipped to each block** as the
primary computational unit (guarantees the pipeline works even where panchayat polygons are
unavailable), and **aggregate grid predictions to panchayat polygons by spatial mean/majority
join wherever a panchayat boundary layer is confirmed available for the pilot district** — this
gives the panchayat-level output the PS asks for without making the whole pipeline depend on a
boundary dataset that (per `03`) is not uniformly available.

```
District → Block → Panchayat (reporting unit, where boundary exists)
                        ↑ aggregation
                 Grid cell (1 km, computational unit, always constructible)
```

The 1 km grid is described honestly as **"a 1 km computational grid used to represent
spatially varying predictors and generate panchayat-level estimates,"** never as "1 km accurate
weather forecast" — accuracy is a property of the validated model output, not of the grid
resolution itself. The user-facing output is always the **Panchayat-level forecast**; the grid
is an internal computational representation feeding that output.

### Grid-to-panchayat aggregation method (must be documented, not assumed)

Once the ML model scores every 1 km grid cell inside a panchayat, those cell-level predictions
must be aggregated into a single panchayat-level value:

- **Temperature (max/min):** **area-weighted mean** of the grid cells whose centroids fall
  inside (or, for cells straddling the boundary, whose intersection area falls inside) the
  panchayat polygon — a cell is weighted by the fraction of its area that lies within the
  panchayat, not counted as a whole cell for a partial overlap.
- **Rainfall:** **area-weighted mean**, using the same intersection-area weighting, since
  rainfall totals over an area are naturally an area-weighted quantity. Cells intersecting a
  panchayat boundary are split geometrically (via a GIS intersection, e.g. `geopandas.overlay`)
  and weighted by the resulting intersected area, not simply included/excluded by centroid.
- **Humidity/wind (if built):** area-weighted mean, same method, unless a documented reason
  (e.g. non-linearity of the variable) calls for a different statistic — any deviation from
  area-weighted mean must be stated and justified in this file, not silently substituted.

This intersection-and-weight step is real GIS logic (`geopandas`/`shapely` polygon overlay), and
must be implemented and tested (`tests/` GIS suite, `10_TESTING_DEPLOYMENT_AND_PPT.md` §1) —
"average the cells that seem to be inside" without explicit boundary handling is not acceptable.

## 3. ML training pipeline

```
Raw Data → Data Validation → Spatial Alignment → Temporal Alignment → Missing-Value Handling
   → Feature Engineering → Train/Val/Test Split (spatial, see below) → Model Training
   → Hyperparameter Tuning → Validation → Spatial Generalisation Test → Model Export → Inference API
```

**Split strategy — why not random row split:** a random row-wise split would place
observations from the *same panchayat/grid cell on nearby dates* in both train and test sets,
letting the model "memorise" a location's bias rather than learn a generalisable
coarse-to-local relationship — this inflates reported accuracy in a way indistinguishable from
overfitting, and violates Rule 2/3 (no unearned accuracy claims). Instead:

- **Spatial split**: hold out a subset of panchayats/grid cells entirely (never seen in
  training) to test whether the model generalises to *new locations* — this is the primary
  reported metric, since the ultimate goal is predicting for panchayats which may have thin or
  no historical ground truth.
- **Temporal split**: hold out the most recent time window (e.g., last N weeks) to test
  whether the model generalises to *new dates/conditions* (e.g., different season).
- **Spatio-temporal split**: combine both — hold out some locations for some periods — as the
  most rigorous but most data-hungry option; used if pilot data volume allows.

## 4. Evaluation

Per variable (temperature first, then rainfall, then humidity/wind if built), report on the
**spatial holdout set**: MAE, RMSE, bias (mean error), correlation (R), and R². Every one of these
numbers is `null`/`"not_yet_evaluated"` until Phase 6 actually runs — no placeholder or
illustrative figure is ever written into this documentation, the API, or the dashboard as if it
were a result. For rainfall,
additionally report rain-occurrence classification metrics (precision, recall, F1 for "rain
occurred" vs. "no rain") alongside the continuous-amount metrics, since rainfall error
distributions are highly non-Gaussian and a plain RMSE can be misleading on its own (see
`04_ML_DOWNSCALING_APPROACH.md` §5).

Always report the **Block Replication Baseline vs. ML model** side-by-side (plus the optional
IDW-across-neighbouring-blocks secondary baseline where applicable, per
`04_ML_DOWNSCALING_APPROACH.md` §0) — e.g.:

```text
                MAE
Baseline (block replication)   not_yet_evaluated
ML (LightGBM)                  not_yet_evaluated
Improvement                    not_yet_evaluated
```

Values are filled in only after training/evaluation actually runs — never manufactured in
advance (Rule 2/3). An ML model that doesn't beat the Block Replication Baseline for a given
variable is not shipped as "the downscaler" for that variable; it is reported as a negative
result and investigated (model choice, features, or — on synthetic data only — the generator's
signal-to-noise, per `11_AGENT_BUILD_PLAN.md` §2.5) rather than hidden.

## 5. Implementation phases

| Phase | Objective | Key outputs | Acceptance criteria |
|---|---|---|---|
| 1 | Problem understanding & research | This documentation set | Internally consistent, no fabricated sources |
| 2 | Dataset acquisition | Pilot district chosen; raw data pulled for coarse forecast + all static features | All Section-03 datasets confirmed accessible for the chosen district, or explicitly logged as unavailable with a fallback |
| 3 | Data preprocessing | Cleaned, aligned feature store | Schema validated, spatial join success rate reported |
| 4 | Baseline model | Block Replication Baseline implemented & evaluated for temperature and rainfall (mandatory); optional IDW-across-neighbouring-blocks secondary baseline if applicable | Baseline metrics reported (not claimed as "the solution") |
| 5a | ML downscaling — **temperature (first MVP target)** | LightGBM quantile model trained for max/min temperature | Temperature model evaluated against the Block Replication Baseline on spatial-holdout MAE/RMSE; result reported honestly whichever way it goes |
| 5b | ML downscaling — **rainfall (second MVP target)** | LightGBM single-stage quantile regression model trained for rainfall (the MVP default — see `04_ML_DOWNSCALING_APPROACH.md` §5; the two-stage rain/no-rain-then-amount model is an optional Phase-2 enhancement, not a Phase-5b choice) | Rainfall model evaluated against the Block Replication Baseline, including rain-occurrence precision/recall/F1, only attempted after Phase 5a is validated |
| 5c | ML downscaling — additional variables (optional) | Humidity/wind models, same pipeline, only if 5a/5b are complete and time remains | Same acceptance pattern as 5a/5b |
| 6 | Model evaluation | Full metrics report, spatial/temporal error maps, for every variable actually built | Metrics reported honestly, including where the model underperforms |
| 7 | Inference API | FastAPI `/prediction` endpoints live | Returns point + uncertainty interval/label + data-source tag |
| 8 | GIS dashboard | React/Leaflet dashboard | Drill-down District→Block→Panchayat works; coarse-vs-downscaled toggle works; a persistent attribution line ("BHOOSAMPADA, NRSC (ISRO)" / Copernicus, per `03` license column) is visible on the map (Leaflet's built-in attribution control, extended with these entries — not just the default "© OpenStreetMap") |
| 9 | Advisory engine | Rule engine + `/advisory` endpoint | At least 3 advisory types functioning, each showing `uncertainty_label`-linked suppression logic (downgrading on `high`, never `low` — `04` §3) |
| 10 | Integration | All services wired via Docker Compose | `docker compose up` runs the full stack locally |
| 11 | Testing | Test suites per `10_...md` | Critical-path tests passing |
| 12 | Deployment | Deployment doc followed, demo-ready build | Runs fully offline for judging, with the sole documented exception of Leaflet basemap tiles (`05_SYSTEM_ARCHITECTURE.md` §7) |
